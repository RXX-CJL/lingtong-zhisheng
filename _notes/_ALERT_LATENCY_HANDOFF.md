## 二、给 GPT6 的线索包：告警栏延迟

### 2.1 现象（用户口径）

> "右边栏违规告警和视频左上角的报告显示还是有一定延迟，视频左上角的报告反馈速度我很满意，
> 但是违规告警还差一些（虽然有所改进）……**还是将近有 3 秒的延迟**"

同一时刻，左侧「**正常通行**」栏的反馈用户认为**很快**。

### 2.2 已实测排除的环节（**都有数字，别重复劳动**）

| 环节 | 实测值 | 怎么测的 |
|---|---|---|
| 后端 → 接口可见 | **0ms**（判定成立与接口返回在同一采样点） | `_scripts\_measure_alert_latency.py`（50ms 高频采样） |
| **事件引擎**耗时 | **0~0.2ms，峰值 10~11ms** | `/status` 的 `event_engine_ms` / `event_engine_max_ms`（我新加的） |
| 前端：WS 收到 → DOM 出现 | **152~277ms**（含当时 150ms 去抖） | 页面内埋点 `window.__alertLatency`（我新加的） |
| 去抖本身 | 已**按用户判断删除**（150ms 无实测依据，占端到端一半） | `LiveMonitor.connectViolationWs` 内注释 |
| `/status` 与 `/vehicles` | **同一个 HTTP 请求**里返回，同一帧数据 | `routers/realtime.py` `/vehicles` 返回 `{clean, violators, traffic_lights}` |
| WebSocket 推送链路 | 已修通（曾被静默吞掉 + Vite 代理未开 `ws:true`） | `/status` 的 `ws_push.push_scheduled`（实测与 `violation_count` 一一对应） |

**合计已解释：< 0.5 秒。剩下约 2.5 秒未解释。**

### 2.3 我的假设（**未证实，请优先验证或推翻**）

**假设 A：画面上的标注比"判定成立"更早出现。**
事件流程（`realtime_detector.process_frame`）：

```
① `violations = check_violations(...)` 拿到候选
② `_viol_hold` / `cooldown` / `loop_dedup` 闸门  ← 违规要被"确认"
③ `self._last_violations = violations`            ← **画面标注用这个**
④ `_push_recent_violations(violations)`           ← **告警栏用这个**（同一个列表）
⑤ 画框 → ⑥ 存证据/事件视频 → ⑦ 事件引擎
```
②③④ 在同一帧，所以理论上应该**同时**。
**但如果渲染器实际用的是"闸门之前"的候选违规**，画面就会提前出现标注 ——
请**核对 `_draw_detection_boxes` 被传入的 `violations` 是不是 `self._last_violations`（已确认）**，
以及**有没有第二条绘制路径**（我更早前修过"主循环 + 兜底循环"两处绘制）。

**假设 B：MJPEG 流有一帧以上的缓冲，而告警栏没有。**
画面走 `multipart/x-mixed-replace`，浏览器/uvicorn 可能有 1~N 帧缓冲；
告警栏是"推送 → 拉取"。**若流缓冲多帧，画面看起来会比真实时间更早**（相对而言）。
验证：`/status` 里加"最近一帧的 seq + 生成时刻"，与浏览器端 `img` 的显示时刻对照。
—— 我**没**做到这一步就交给了用户（见 §一），这是**最可能出结果的一条**。

**假设 C：`hold_sec`（默认 1.5 秒）**。
若渲染器画的是"未确认的候选违规"，则画面比"确认"早 `hold_sec` + 检测周期
（1.5s + ~0.4s ≈ **1.9s**）—— 与用户说的"将近 3 秒"同一量级。
**这条最容易验证**：把 `hold_sec` 临时设成 0（`POST /api/realtime/settings {"hold_sec":0}`），
**若延迟立刻消失，假设 C 成立**。

### 2.4 相关代码位置（精确到函数/字段）

| 位置 | 说明 |
|---|---|
| `realtime_detector.process_frame` | 违规判定 → 闸门 → `_last_violations` → 推送，全在这里 |
| `realtime_detector._draw_detection_boxes` | 画面标注入口；`violations` 默认取 `self._last_violations` |
| `realtime_detector._push_violation_event` | WebSocket 推送；**我已把它提前到"画完框"那一刻** |
| `realtime_detector._push_recent_violations` / `_push_repeat_alert` | 告警栏数据源（`RECENT_VIOLATION_TTL=10s`） |
| `routers/realtime.py` `/vehicles` | `{clean, violators}` 一次返回 |
| `LiveMonitor.vue` `connectViolationWs` / `refresh` / `window.__alertLatency` | 推送接收 + 端到端埋点 |

### 2.5 建议的最短验证路径（按性价比排序）

1. **把 `hold_sec` 设为 0，看延迟是否消失** —— 一条 curl 就能定假设 C
2. **看用户控制台那两行数字**（前端侧 / 服务端起算）—— 立刻区分"前端慢"还是"后端发得晚"
3. 若"服务端起算"就接近 3 秒 → **假设 A/C 成立**，去查"画面标注用的是哪一份违规"
4. 若"前端侧"就接近 3 秒 → 查 `refresh()` 的请求为何慢（当时是否有并发/阻塞）

### 2.6 ⚠ 别踩的坑（我踩过）

- 我前两轮**只测接口**就宣布"修好了"（接口确实 10 秒内有数据），但用户看到的**页面**不是那回事 ——
  **必须同时记录"接口返回什么"和"DOM 显示什么"**（`_uicheck\_run_panel_dom_check.mjs`）
- 我去抖 150ms 是**随手定的**，占掉端到端一半；用户直接质疑"这个没用了吧" —— **他是对的**。
  写代码时"临时值"必须标明依据，否则后人（包括我自己）会当成设计。
- 这个项目的浏览器测量效率极低（违规每 30~40 秒才一次，200 秒采样只抓到 2 个样本）——
  **这类"盯运行"的活应该交给用户**（他有眼睛、有控制台、能实时并发操作）。
