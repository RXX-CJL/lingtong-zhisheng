## 一、✅ 播放太快（点 1）

**事实**：
- 事件视频的逐帧回放（`EventDetail.vue`）已改成**按 sidecar 的 `time` 最近邻取帧**，
  语义正确；旧 sidecar 才回退 `round(t*fps)`。
- 但**旧事件视频本身仍是 2×**：写死 10 fps 写盘、实际源 20 fps。
  上次按用户要求**只重封了 `evt_11200_18_60c808`**，其余 4800+ 个没动。

**待做**：
1. 明确"原始证据"具体指哪个（事件视频？关键帧三联图？）——**需要用户确认**。
2. 若指旧事件视频：可选
   - (a) 提供一个**批量重封脚本**（`setpts=0.5*PTS`，只对新产生的或指定 ID 生效）
   - (b) 接受旧视频，**新录制的已经是正确速度**（`_ev_fps` 已按片段跨度推导）
3. 若指 `EventDetail` 的回放倍率：那里已有诊断字段
   （`检测数据源时间跨度 … 媒体时长 … 回放倍率 …×`），可据此判断是否视频本身 2×。

## 二、🟡 识别框帧率（点 2）

**已做**：`YOLO_IMGSZ=960` + `FRAME_RATE=6` + 裁掉 `license_plate` + **框位置预测** →
框的重定位间隔 558 → **378 ms（−32%）**，且框在两次检测之间**连续滑动**（已验证）。

**天花板**：模型只占 139 ms，**单帧总成本 ~378 ms 的大头在非模型环节**
（JPEG 编码 / 标注绘制 / 事件引擎 / 证据落库）。

**用户态度**：**"先这样吧，也快了不少了"** → **本轮不排期**。
若将来要再优化，第一步是**拆解这 ~240 ms**（脚本 `_bench_stages.py` 已有骨架，
但要注意它上次因 `check_violations` 签名传错 + 冷启动而失真）。

## 三、🔴 每辆车两个框（点 3）——本轮最需要补充信息的一条

**实测（当前配置，1920×1080 演示帧）**：
```
检出 19 个框   按来源: {vehicle:3, traffic_light:9, lane:7}
车辆类框 = 3 个（3 辆车）→ 重叠对（IoU>0.5）= 0 对
```

**机制上的隐患（确实存在）**：
1. `image_recognizer.multi_model_detect` 的去重键是 **`(class_name, 原始 bbox 元组)`** ——
   **只有像素完全相同才算重复**。同一辆车被两个模型检出、框差 1 px，就**都会留下**。
2. `vehicle` 与 `license_plate` **实际加载的是同一个 `yolov8s.pt`**（T11/G4）：
   两个 key 各跑一次、各画一次 → **同一辆车两个框**。旧配置（5 模型）下必然出现；
   裁掉 `license_plate` 后消失（这正是本轮实测 0 对重叠的原因）。
3. `helmet_best.pt` 也可能检出车身。

**待做**：
1. **先复现**：请用户说明是**在哪个视频/哪次演示**看到两个框（旧配置 or 新配置？）
2. 无论原因，建议在 `annotation_renderer` 的**主绘制循环前**加一层
   **车辆框 IoU 去重**（保留置信度最高的那个）——红绿灯已有同类实现
   `_dedupe_traffic_lights`（`annotation_renderer.py:599`），**照着做即可**，属低风险改动。
3. 可选：`multi_model_detect` 里**同一模型文件只跑一次**（`vehicle` 与 `license_plate`
   都指向 `yolov8s.pt`，重复跑纯浪费）。

## 六、🟡 timeout of 15000ms（点 6）

**事实**：
- `15000` 来自 `web-admin/src/api/index.js` 的**两个 axios 实例统一超时**
  （`request` 走 Vite 代理 `/api`；`realtimeRequest` 直连 `:8001`）。
- 空闲时实测**全部接口 1~35 ms**：`/status` 35、`/vehicles` 15、`/evidence` 23、
  `/events` 22、`/system/models` 2、`/cloud/statistics` 4、`/devices/list` 1 …
- → **不是常态慢**，而是"某个瞬间被卡住"。

**最可能的成因（按概率）**：
1. **检测运行中**：后端 2.65 fps 跑 YOLO，GPU/CPU 饱和，此时突发请求可能排队数秒；
   若用户同时又开着 CARLA（实测帧率掉到 1.5），更容易撞线。
2. **`getEventVideoUrl` / 关键帧图片**这类**大文件**（事件视频 2.5 MB/个、
   关键帧 0.54 MB）在弱网/并发下超时。
3. **MJPEG 长连接占满浏览器同源连接数**（6 个），使其他 XHR 排队 ——
   这与用户已发现的"**刷新才卡、关掉重开就好**"**同源**，很可能是**同一个根因**。

**待做**：
1. 现场复现并**记录是哪个 URL 超时**（前端 logger 已记录 `HTTP FAIL ... cost=...ms`，
   在「系统设置 → 系统日志」页能看到）——**这是最快定位手段**。
2. 若确认是"检测运行时请求排队"：给重接口**降优先级**、或前端轮询加**退避**
   （连续失败则延长间隔），而不是简单调大 timeout（那会把真故障也掩盖）。
3. 修 MJPEG 连接泄漏（见 `_SESSION_HANDOFF.md` 优先级 1）——**一箭双雕**。

## 八、🔴🔴 云端开关"自动打开"（点 8）——**本轮最严重的发现**

**结论：成立，且机制已经找到。**

### 机制：`pushSettings()` 会**连带推送两个付费开关**

```javascript
// web-admin/src/views/LiveMonitor.vue:573
async function pushSettings() {
  await api.post('/realtime/settings', {
    enabled_types: settings.enabled_types,
    min_confidence: { _default: confDefault.value },
    hold_sec: holdSec.value,
    cooldown_sec: cooldownSec.value,
    cloud_consult: settings.cloud_consult,   // ← 顺手推
    cloud_review:  settings.cloud_review,    // ← 顺手推（★最大开销开关）
    display_mode: displayMode.value,
  })
}
```
而 `pushSettings` 被**检测项勾选、置信度滑条、确认时长、冷却期**等多处控件调用
（`LiveMonitor.vue:170/175/181/184`）。

**后果链**：
1. 用户在 RealTimeMonitor 里**勾掉某个检测项**（或拖一下置信度）
   → 触发 `pushSettings()`
   → **把 `cloud_review` / `cloud_consult` 按"内存里的当前值"写回后端**。
2. 若内存里的值**不是用户以为的值**（例如用户刚在设置页关了，但 RealTimeMonitor
   从未 `loadSettings()`；或 `loadSettings()` 因超时走了 catch 分支没赋值；
   或组件默认值 `cloud_review: true`），就会**静默把开关打开**。
3. 用户看到的现象正是：**"我明明关了，进某个页面点一下就又开了"**。

**佐证（后端侧是对的）**：`update_runtime_settings()` **只更新传入的字段**
（`if "cloud_review" in patch:`），不传就不动 → **问题 100% 在前端的"连带推送"**。

**待做（建议三条一起）**：
1. **拆开推送**：`pushSettings()` 只推它自己那几项（`enabled_types`/`min_confidence`/
   `hold_sec`/`cooldown_sec`/`display_mode`），**不再带 `cloud_review`/`cloud_consult`**；
   两个开关**只由各自的控件单独推送**（`pushCloudReview()` 已是这个写法，照抄即可）。
2. **消除 fail-open**：`loadSettings()` 的 `catch` 分支目前**静默忽略** →
   应改为"读取失败就把开关**置灰并提示**"，绝不让界面显示一个未同步的状态；
   同时把组件默认值从 `true` 改成"未知"，避免"没读到=开着"。
3. **加服务端审计**：`/api/realtime/settings` 已记录 `logger.info("[settings] 运行时设置已更新: keys")`，
   可扩展为**记录来源 IP + 变更前后值**，这样"谁把它打开的"可追溯。

> 这条建议**优先于其它所有**：它是**真金白银**的问题（每次违规事件都打 2~3 家云 API）。

## 九、录制违停等 CARLA 视频：值不值得？

**值得，而且是当前性价比最高的"功能扩展"**。理由与前置条件：

| 项 | 结论 |
|---|---|
| 判定逻辑 | ✅ **已完整**（`behavior_engine.analyze_illegal_parking`：静止 + 在禁停区内 + 持续 ≥ `park_duration_threshold`(5s)） |
| 阈值 | ✅ 已是用户口径（2026-10-04 从 300s 改成 **5s**） |
| 场景标注 | ✅ 标定面板已能画「禁停区」多边形（`no_parking_zones`） |
| 现存素材 | ⚠️ 演示视频里有停着的车，但**不足 5 秒**，所以没触发过 |
| **需要录什么** | 一个**20~30 秒**的 CARLA 片段：车辆在禁停区内**静止 ≥ 5 秒**（最好 8~10 秒留余量） |
| 录制成本 | 低：`_scripts\_demo_scene.py` / `_carla_record*.py` 已有骨架；CARLA 启动 + 录制约 10~20 分钟 |
| **必须先问用户的** | ① **帧率**（用户此前明确"**应 60fps 以上**"，但现有素材都是 20fps —— 录制前必须确认） ② 分辨率 ③ 用哪个机位（现演示机位是纵深机位，**违停判定不需要横向机位**，可复用） ④ 车辆行为（静止不动；**不要** `enable_constant_velocity`） |
| 风险提示 | 录制时 **CARLA 与后端抢 8 GB 显存**（实测帧率 2.77→1.5）→ **建议先停后端** |

**建议的录制顺序**（一条视频验一个功能，避免互相干扰）：
1. **违停**（最好做，逻辑+阈值都就绪）
2. **压线**（需要先给标定面板加"车道线"标注 —— 见 `_SESSION_HANDOFF.md`；
   `_extract_lane_lines()` 挑的类名 COCO 不输出，所以现在还判不了）
3. **逆行**（**需要用户先定"车道方向怎么配"**，且纵深机位下"画面左右"推不出方向，
   可能要**换横向机位重录**）
4. **超速**（标定已完成，只需让车明显超速）

# 十二、★补充核实（2026-10-09，用户追加信息后；**本节优先级最高**）

## 12.1 🔴🔴 "开久了像断网" + 红字报错 —— **根因已定位到代码级**

**用户原话**：
> "读取运行时设备失败 / 加载设备列表失败 / timeout 15000ms 都是管理端**开久了之后**
>  会在网页上端出现红字报错提示，而且开久了以后管理端会**像断网了一样**，现在也是
>  （我记得之前有做类似于日志一样的东西，如果你不清楚为什么可以去看看）"

### 根因：MJPEG 流生成器**不检测客户端断开** → 僵尸生成器耗尽线程池

```python
# api/routers/realtime.py:169
async def generate():
    while True:                                    # ← 无限循环
        frame = await asyncio.to_thread(realtime_detector.get_annotated_frame)  # ← 占线程池线程
        ...
        await asyncio.sleep(0.05)
        # ★全程没有 request.is_disconnected() 检查
```

**机制链**（每一环都有代码/实测支撑）：
1. 浏览器刷新 / 关页 → 旧 MJPEG 连接的**生成器何时退出不受控**（只靠下次 `yield` 写失败才发现，
   而 `yield` 之间还有 `sleep(0.05)` 与 `to_thread`）。
2. `get_annotated_frame` 是**重活**（实测流帧间隔 ~217 ms，即每帧花 ~170 ms：
   绘制 + JPEG 编码），而且走 `asyncio.to_thread` → **每个活跃流长期占用一个线程池线程**。
3. `asyncio.to_thread` 用的是**默认 ThreadPoolExecutor**（CPython 默认 `min(32, cpu+4)` 个工作线程）。
4. 刷新几次（或开多个标签页）→ **僵尸流累积 → 线程池被占满** →
   **所有走线程池的接口一起排队** → 前端表现为 `timeout of 15000ms exceeded`
   + 整站"像断网"。
5. 这**同时解释**了用户此前的两条独立观察：
   - "**关掉页面再打开就正常，用浏览器刷新却容易卡住**"
   - "**开久了像断网**"（现在也是）

**为什么"关掉重开就好"**：关标签页会让浏览器彻底断开 TCP，服务端连接计数归零；
而"刷新"只是新开一条流，旧的还在。

### 修法（下一个对话执行）

| # | 改动 | 位置 | 说明 |
|---|---|---|---|
| 1 | 生成器里加**断开检测**：每轮 `if await request.is_disconnected(): break` | `routers/realtime.py` `generate()` | 需要把 `Request` 传进生成器。这是**根治** |
| 2 | 加**并发流上限**（如 3 条），超出则返回一张"已有 N 个监视窗口连接"的诊断帧并正常结束 | 同上 | 防标签页/多显示器场景再次堆死 |
| 3 | **给流单独开线程池**（不要把重活丢进全局默认池），避免拖垮非流接口 | 同上 | 或把流帧率上限写死（如 ≤5 fps） |
| 4 | 前端 `beforeunload` 里主动 `img.src = ''` 释放 `<img>` | `LiveMonitor.vue` | 让浏览器尽快断开 |
| 5 | 兜底：把 `generate()` 的每帧 sleep 提到 0.1~0.2（流 5~10 fps 已足够，画面本来就靠预测框平滑） | 同上 | 直接减半线程占用 |

## 12.6 ★★两个"画面不干净"的问题 —— **根因已定位**（2026-10-09 用户追加）

> 用户原话："标定和标注感觉还是存在问题（**左边不该识别的红绿灯还是识别了**），
>  而且画面中甚至还**识别了路旁的盆栽**"

### 问题 1：左侧那盏黄灯被画出并判色

**实测证据**（从 `_rt_trace_final.jsonl` 249 条 trace 统计每盏灯的 (颜色, 左上角)）：
```
('red',    (816, 123))   424 次     ← 主画面灯（受控方向之一）
('red',    (1645, 902))  322 次     ← CAM-2 小窗里的灯
('red',    (1324, 161))  258 次
('yellow', (419, 120))   252+228 次 ← ★ 画面**左侧**那盏黄灯（横向车道）
('red',    (275, 182))   200 次     ← ★ 更左还有一盏红灯
('red',    (999, 124))   172 次
('red',    (1129, 120))  166+140 次
```

**根因**：`_collect_traffic_lights()` 会把**画面里所有**被检出并判色的灯都塞进
`self._last_traffic_lights`，而渲染器会**把它们全部画出来**（带颜色标签）。
灯态判定确实只认 ROI 内的灯（`_scene_light_state_from_cnn(rois=...)`），
**但"画出来的框"没有任何 ROI 过滤** —— 于是用户看到"左边不该识别的红绿灯还是识别了"。

**修法**：给**绘制**也加 ROI 过滤 —— 已有现成的静态方法 `realtime_detector._light_in_rois(bbox, rois)`，
只需在 `_collect_traffic_lights()` 返回前：
- 若 `scene_config` 里有 `traffic_light_roi` → **只保留中心落在 ROI 内的灯**；
- 没有 ROI 时保持现状（全部画，便于用户第一次标定时找灯）。

> ⚠ 注意别把"判色链路"一起裁掉：灯态汇总用的是同一个 `_last_traffic_lights`，
> 而它**本来就已经**按 ROI 过滤（`_scene_light_state_from_cnn`）。
> 所以这里要**先汇总灯态、再过滤绘制列表**，或者让绘制侧单独过滤，避免改变判定语义。

### 问题 2：路旁的盆栽被画成框

**根因**：渲染器的主绘制循环**只跳过红绿灯，其余全部照画**：
```python
# annotation_renderer.py:398-403
cls = (det.get("class_name") or "").lower()
if cls in ("traffic light", "traffic_light", "red_light", ...):
    continue                      # 只跳过红绿灯
# ↓ 其余一律 cv2.rectangle(...) 画出来
```
而 `CLASS_CN_MAP`（`image_recognizer.py:35`）有 **107 个类名**，其中 **83 个与交通无关**
（`potted plant` / `fire hydrant` / `sports ball` / `chair` / `bench` / `dog` / `cake` …）。
只要上游 YOLO 输出它们，就会被画到画面上。

**修法（推荐在做检测时就过滤，而不是只在绘制时过滤）**：
1. 在 `image_recognizer` 里新增 `TRAFFIC_CLASS_WHITELIST`，只放：
   `car / truck / bus / motorcycle / bicycle / person / rider /`
   `traffic light / red / green / yellow /`
   `helmet 系（with_helmet / without_helmet / no_helmet / helmet）/`
   `plate 系（license_plate / car_plate / plate）/ lane 系（lane_line / road_line / white_line / yellow_line）`
2. 在 `realtime_detector.process_frame()` 里 `detections = self._yolo_detect(frame)`（`:764`）之后
   **过滤一次**，再赋给 `result['detections']`（`:769`）。
3. **顺带收益**：垃圾框不再进入 `all_detections` → 规则引擎/行为引擎/跟踪器都少受干扰，
   `license_plate` 那类"回退 COCO 吐垃圾"的隐患也被彻底兜住。

> ⚠ 注意：过滤要**基于白名单**，而不是"排掉盆栽"——因为 COCO 的无关类有 80 个，
> 只排一个等于掩耳盗铃（且下一个视频会冒出别的垃圾）。

### 验证方式（都很轻）

| 验证 | 方法 |
|---|---|
| 灯 ROI 过滤生效 | `/status` 无直接字段；可对比修复前后 trace 里 `lights` 的 bbox 集合是否只剩 ROI 内的 |
| 垃圾类被挡掉 | 修复后 trace 里不应再出现 `potted plant` 等类；`traffic_light_stats.total` 可能下降（正常） |
| **不回归** | 跑 `_scripts\_evaluate_redlight.py`，确认"每循环恰好 1 次真违规、0 误报"仍成立 |
