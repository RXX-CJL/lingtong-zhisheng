# 智瞳灵声 · 项目方向

> 2026-11-18 定稿。**接手者先读这一份再动手**，否则容易把力气花在已经论证过走不通的路上。
> 本文只回答一个问题：这个项目要做成什么、不做什么、为什么。

---

## 一句话

**用路口已有的摄像头，做交通流量采集与信号配时优化建议，用 CARLA 做效果验证。**

不是电子警察，不是执法系统，不是共享单车治理平台。

---

## 一、三个被否掉的方向（不要再回头）

### ❌ 执法 / 电子警察

**否掉原因：政策壁垒，不是技术壁垒。**

- 执法权在交管部门，个人或公司采集的视频不能直接作为处罚依据
- 交管 12123 是官方入口，用户没有理由换
- 政府采购看资质、稳定性、售后，不看算法新不新

技术做得再好也进不去。这条路从第一句就站不住。

### ❌ 市民举报端

**否掉原因：需求是伪的。**

- 交管已有 12123 和各地随手拍渠道
- 我们提供不了执法资格，举报了也无法处置
- 参与者没有正反馈，留存为零

### ⚠️ 校园共享单车治理（降级为应用场景，不做主线）

**否掉为主线的原因：价值长在运营里。**

- 检测乱停本身技术含量低（YOLO 认 bicycle + 区域判定）
- 真正的价值在于持续运营、持续调度——学生项目做不到
- 学校只有一家供应商（哈啰）时，连品牌识别都用不上
- 不落地就什么都不剩

**保留的部分**：作为"同一套检测能力可迁移到其它场景"的例证，PPT 里一句话带过。

---

## 二、主线：信号配时优化建议 + CARLA 验证

### 做什么

```
路口视频 ──► 流量统计（车/人/排队长度/延误）
          ──► 配时算法（Webster / 绿波带 / 感应控制）
          ──► CARLA 仿真验证（同一路口，原方案 vs 优化方案）
          ──► 输出：可复现的优化建议报告
```

### 为什么是这条路

1. **技术含量在三个方向里最高**：有算法、有实验、有对比数据
2. **结果可量化**：平均延误、排队长度、通行量，能被复现和质疑
3. **CARLA 资产现成**：`api/carla_source.py` 已能读信号灯状态，场景库丰富
4. **不依赖任何人的授权**：不需要交管给接口，不需要平台配合

### 关于"只能提建议"

**这不是缺陷，是交通工程的标准业务模式。**

交通咨询公司、高校交通学院做的工作就是：采集数据 → 分析 → 出配时建议 → 交给交管。
决策权永远在政府手里，技术方永远是建议方。

真实路口**没法做实验**（不能拿真路口试配时），所以仿真不是退而求其次，是**唯一能拿出"A 方案比 B 方案好多少"证据的手段**。

## 三、差异化在哪

**不谈"我们发明了自适应控制"——那个一二线城市已经做了。**

谈成本：

> 自适应信号控制不是软件问题，是硬件问题：地磁、线圈、雷达，每个进口道都要布，
> 一套几万到几十万。全国几百万路口不优化，不是不知道能优化，是装不起检测器。
> 我们用路口**已有的摄像头**完成同样的采集，把门槛从"几十万"降到"零硬件投入"。

行业现状（多来源口径不一，引用时注明）：
- 约 63% 的城市交叉口仍采用固定周期控制（交通运输部 2022 口径）
- 一线城市核心区自适应覆盖率 80%+，深圳联网率 98%
- 三四线城市仍处于联网信号机替换阶段

**我们的市场是"没有预算部署专用检测器的路口"，不是和 SCATS／海信／银江抢有预算的路口。**

## 四、哪些技术资产是可用的（别重复造）

| 资产 | 位置 | 在主线里的作用 |
|---|---|---|
| 实时检测与跟踪 | `api/realtime_detector.py` | 流量统计的输入 |
| 速度标定（像素→米） | `api/speed_calibration.py` | 排队长度、延误的计算基础 |
| 事件引擎 | `api/traffic_event_engine.py` | 拥堵/异常事件的记录 |
| 场景标注（ROI/停止线/车道） | `api/scene_annotation.py` | 路口几何定义 |
| CARLA 接入 | `api/carla_source.py` | 仿真验证的运行环境 |
| 2D 俯视孪生 | `api/routers/twin.py` + `Twin2D.vue` | 路口状态可视化 |
| 管理端 | `web-admin/` | 数据展示与报告导出 |

**这些代码全部保留。** 换方向不等于推倒重来，主线只是把它们串成一条新的链路。

## 五、下一步（按顺序）

1. **确认 CARLA 场景**：找一个带信号灯的标准十字路口，能改配时
2. **流量统计模块**：从现有检测结果里算车流量、排队长度、延误
3. **配时算法**：先做最经典的 Webster 单点配时，别一上来就搞强化学习
4. **对照实验**：同一路网、同一车流，原配时 vs 新配时，跑出数据
5. **小范围真实验证**：拿一段真实路口录像跑流量统计，证明数据是真的

## 六、答辩时的话术（防追问）

| 老师可能问 | 怎么答 |
|---|---|
| 这和现有的自适应信号控制有什么区别？ | 他们需要专用检测器，我们用已有摄像头，成本差一个数量级 |
| 仿真结果能代表现实吗？ | 不能完全代表，但能做真实世界做不到的对照实验；真实数据用来校准仿真参数 |
| 你们能控制真实红绿灯吗？ | 不能，也不打算。我们的输出是优化建议报告 |
| 有没有真实路口数据？ | 有（如果有），用来校准；没有的话用公开数据集 + CARLA |
| 为什么不直接做执法？ | 执法是政策壁垒，不是技术问题，我们不做进不去的市场 |

## 七、判断依据（供后续调整时参考）

这份方向是**当前信息下的最优解**，不是不可更改的教条。

如果出现以下情况，可以重新评估：
- 拿到了真实路口的数据合作（价值立刻上一个台阶）
- 学校/园区愿意付费试点（B 端场景成立）
- CARLA 验证跑不通（技术地基不成立，要换验证手段）

**换方向的前提是「出现了新证据」，不是「做不下去了想换」。**
