# 智瞳灵声项目优化设计

> 版本：v1.0（方案稿）  
> 日期：2026-09-25  
> 范围：基于当前 FastAPI + Vue 主线、TASK-COORD-001 至 007 的执行报告，以及 CSDN 参考文章《多功能智能交通系统-pyqt5、python、pytorch、yolo》整理。  
> 性质：设计与任务路线图；本文件不代表方案已实现或已验收。

## 1. 设计目标

让“智瞳灵声”从能展示单次事件的原型，逐步成为数据可信、性能可测、规则可配置、证据可追溯的交通事件分析系统。优化顺序为：

1. 先保证视频时间轴、推理时间轴、车辆轨迹和回放数据一致。
2. 再使事件判定可解释、场景参数可配置，避免规则与单一视频视角绑定。
3. 统一事件、车辆、证据和统计的数据契约，减少前后端各自拼装事实。
4. 以实测指标推进性能和识别质量，不把模型文件存在等同于能力可用。
5. 保留现有 FastAPI/Vue、SQLite 和本地 YOLO/Tracking 主线，按边界逐步收敛，不进行一次性重写。

## 2. 参考项目中可借鉴的设计

参考文章将交通视频处理拆为检测、识别、跟踪、数据分析和展示，并提供视频、车辆信息、违规列表及统计视图。其特别有价值的工程思想是：

- **场景预标定**：由操作者标出停止线、车道线、斑马线、信号灯区域、虚拟检测线和有效检测区域，让规则知道“这个摄像头里的道路在哪里”。
- **围绕 track ID 聚合车辆上下文**：速度、方向、车牌/车型和违规状态放在同一车辆对象视角展示。
- **轨迹驱动事件判断**：由多个时刻的位置变化判断越线、方向和流量，而不是只看单帧检测框。
- **事件产物可追溯**：保存事件视频、抓拍和结构化结果，支持后续复核与统计。
- **分析结果与视频界面联动**：视频负责呈现场景，侧栏负责显示较长的车辆信息，避免把全部文字挤在画面上。

这些思想映射到现有工程即可。文章提到的具体旧模型、桌面 GUI、CSV 主存储和特定算法代码属于其实现选择，不应直接成为本项目的技术约束。

## 3. 当前项目状态与设计依据

以下结论来自当前仓库文件和已存任务报告；不同证据等级要继续保留，不能仅因代码存在就视为功能已验证。

### 已有基础

- 主线由 `api/` FastAPI、`web-admin/` Vue、SQLite 事件表、本地 YOLO/Tracking、规则插件、`TrafficEventEngine`、循环帧缓存和 CloudAI 协作组成。
- `TASK-COORD-004` 报告记录真实视频触发 7 个事件，并进入数据库和 EventCenter。
- `TASK-COORD-005` 报告记录事件视频 H.264 播放和关键帧落盘修复。
- `TASK-COORD-007` 报告记录新事件 sidecar、逐帧回放 API 和 EventDetail SVG 检测框展示。
- 管理端已有实时识别页、EventCenter 和 EventDetail；项目已有规则插件、场景感知、证据链和车牌相关代码。

### 需要优先处理的风险

- **采集与推理节奏没有形成一个明确时间契约。** 报告记录视频源曾全速读取，而推理受 `FRAME_RATE` 限制；当前配置默认推理频率为 3 FPS，回放编码默认按 10 FPS。实时流画面刷新和检测框更新频率因此不是同一个指标。
- **推理繁忙时的帧处理规则不够清楚。** 当前进程锁会跳过繁忙期间到来的帧；事件回放又需要逐帧 sidecar。需明确保留最新帧、跳帧策略、时间戳和回放时间的关系。
- **检测、跟踪、规则和云端复核处在同一条处理链上的阻塞风险。** CloudAI 若同步耗时，会影响后续处理和可观测帧率；云端复核应由事件队列独立消费。
- **停止检测时活动事件与证据同步存在边界缺口。** TASK-COORD-007 报告记录 stop 流程可能留下磁盘 sidecar 却没有对应数据库事件行。
- **事件表承载较多 JSON 字段，证据路径与逐帧 sidecar 是文件级关联。** 需要文件格式版本、校验和、写入完成标记及恢复策略，避免事件行指向不完整证据。
- **场景预标定与版本关联尚未形成产品闭环。** 规则结果需要能说明由哪个摄像头、哪个场景配置版本、哪些轨迹和阈值产生。
- **仓库存在多个历史子系统、数据库和未提交改动。** 本轮不据此推断要清理或迁移；先建立只读盘点和数据目录边界，再按独立任务处理。

## 4. 目标架构

```text
视频文件 / 摄像头 / 仿真源
          │
          ▼
统一采集适配层 ── 帧序号、源时间戳、采集时间、分辨率、源 FPS
          │
          ├──────────────► 实时预览流（按显示能力刷新）
          ▼
有界“最新帧”推理队列 ── 队列长度受控、过期帧可丢弃并计数
          │
          ▼
检测器（YOLO）→ Tracker → FrameObservation
                              │
                              ├──► 有界轨迹状态 / VehicleSnapshot
                              │
                              ├──► 场景几何与标定配置
                              ▼
                       规则引擎 / TrafficEventEngine
                              │
               ┌──────────────┴──────────────┐
               ▼                             ▼
       事件证据工作队列                 CloudAI 复核队列
       原视频片段 + sidecar             超时/重试/降级状态
               │                             │
               └──────────────┬──────────────┘
                              ▼
              事件存储 + 媒体索引 + 统计聚合
                              │
                              ▼
         FastAPI（统一契约 / 查询 / 回放 / WebSocket）
                              │
                              ▼
 Vue 管理端：实时监控 / 场景配置 / EventCenter / 事件回放 / 统计
```

这是逻辑分层，不要求立即拆成微服务或引入消息中间件。阶段一可在单进程内用有界队列和独立 worker 实现，明确接口后再评估多进程或外部队列。

### 4.1 帧与车辆数据契约

每个处理结果使用统一、可版本化的数据对象，至少包含：

| 对象 | 必备字段 |
|---|---|
| FrameObservation | `camera_id`、`session_id`、`frame_index`、`source_pts` 或等价源时间、`captured_at`、`inference_at`、`image_width/height`、`detections`、`inference_duration_ms` |
| VehicleSnapshot | `camera_id`、`session_id`、`track_id`、`frame_index`、`bbox`、`class_id/name`、`confidence`、`speed_value/unit`、`direction`、可选 `plate`、字段来源与置信度 |
| TrafficEvent | `event_id`、事件类型、状态、触发时间、`camera_id/session_id/track_id`、场景配置版本、命中规则及参数、关联证据引用、AI 复核状态、人工复核记录 |
| ReplayManifest | 格式版本、源视频 FPS/时间基准、输出编码 FPS、原始宽高、帧数、sidecar 路径、校验信息、检测器/跟踪器版本和场景版本 |

车辆身份只在摄像头会话内解释；业务关联键使用 `camera_id + session_id + track_id`，避免不同视频或重启后重复的 track ID 冲突。未识别到车牌时明确为空/未知，不用占位值伪装识别结果。速度始终附单位和来源；像素速度与公里/小时不能混用。

### 4.2 视频时钟与性能边界

- 分开记录采集 FPS、预览 FPS、检测 FPS、轨迹更新 FPS、回放 FPS；界面不能用单一“FPS”混称。
- 文件回放按源时间戳或源 FPS 节奏推进。实时摄像头按采集时间处理。
- 推理拥塞时采用有界队列和“保留最新帧”的策略，过期帧丢弃必须计数；不得让内存随视频时长增长。
- 推理框只在真实推理或真实跟踪更新时刷新。若前端为了平滑对框做视觉插值，必须标明为显示平滑，不得把插值当成新的检测观测写入事件证据。
- 预览编码、事件录像编码和推理采样各自配置；事件媒体需保存源时间轴映射，避免变速回放时框错位。
- 每个阶段报告平均值与 P95 延迟、队列深度、丢帧率、最近检测更新时间和错误数；优化目标以实测基线设定，不先承诺固定 FPS。

### 4.3 场景标定与规则配置

新增场景配置时建议分为：

1. **图像区域**：ROI 多边形、停止线、虚拟计数线、斑马线区域、车道边界、信号灯区域。
2. **坐标规则**：以视频原生画面归一化坐标 `[0,1]` 保存，显示时变换到当前视频尺寸；校验点落在画面范围内，线段和多边形不能退化。
3. **交通语义**：车道行驶方向、入口/出口、允许方向、信号灯状态关联、适用规则集合。
4. **物理标定**：可选已知距离、地面参考点或单应矩阵，用于速度换算；未完成标定时禁止把像素位移标成真实 km/h。
5. **版本审计**：配置具备 `scene_id/version/effective_at/created_by`；新版本不覆盖已关联事件所用的旧版本。

UI 先支持人工绘制、预览和保存版本；自动识别车道线/斑马线可作为后续建议，不作为第一期阻塞项。每条规则要给出输入条件、窗口/状态、阈值和可解释命中证据，并能按摄像头或场景启停。

### 4.4 事件证据与存储

- 原始证据视频保持不可变；分析回放使用逐帧 sidecar 或可重建的派生视频，绝不覆盖原始证据。
- 事件记录保存媒体引用和状态；大型逐帧数组不长期塞入事件主表 JSON。sidecar 采用可流式读取的格式，并带 `schema_version`、帧数、时间戳、坐标维度、哈希或完整性信息。
- 事件生命周期明确：`detected → recording → evidence_ready → pending_ai → reviewed/closed`，失败分支记录原因；stop/异常退出执行安全收尾并使数据库和媒体索引一致。
- 关键帧、原始片段、回放元数据、分析导出采用明确目录与保留策略；存储清理只按保留策略执行并记录审计，不在本设计阶段删除现有文件。
- SQLite 继续作为当前单机主线。先确认唯一权威 DB 路径、备份/恢复和 schema 迁移规范，再评估是否需要 PostgreSQL；当前没有证据支持立即换库。

### 4.5 API 与 Web 管理端

- 保留 FastAPI，统一 Pydantic/响应契约，明确时间戳统一使用带时区 ISO-8601，内部 epoch 单位和序列化边界固定。
- 实时视频和实时状态数据分流：视频走媒体流；车辆快照/检测指标/事件状态走有版本的 WebSocket 或轮询 API。慢客户端不得阻塞检测 worker。
- EventCenter 消费统一事件摘要；EventDetail 展示原始视频、分析回放、当前帧车辆、事件证据、AI 结论与人工复核，并标明数据来源和缺失原因。
- 实时识别页、事件回放和导出使用同一套中文标签映射与状态词典，车辆属性字段名由 API 决定，不在多个页面重复推断。
- 统计使用规范化事件事实（类型、时间、地点/摄像头、状态）聚合；图表数值可回溯到筛选条件和事件列表。

## 5. 质量与验收体系

每次变更按四层证据报告：

1. **代码存在**：调用路径、数据字段和失败分支可定位。
2. **模块可运行**：单元/契约验证通过；本设计稿本身不执行测试。
3. **真实数据验证**：固定测试视频或摄像头样本产生与预期一致的轨迹/事件/证据。
4. **完整链路验证**：原始视频 → 真实推理与跟踪 → 规则命中 → 事件落库与媒体 → API → EventCenter/EventDetail。

建议逐步形成固定评测集，按场景标注真值，报告：检测精确率/召回率、跟踪 ID 切换、规则事件 precision/recall、车牌准确率（如启用）、采集/推理/预览 FPS、端到端事件延迟、丢帧率、证据完整率、人工复核比例。指标需要先采基线，再设阶段目标；不能从单个视频演示推导普遍准确率。

## 6. 分阶段路线图

### 阶段 A：性能与时间轴基线（最高优先）

目标：明确真实文件回放为什么推理框更新慢，并让文件源按时间推进。

- 采集、预览、推理、跟踪、回放的时间戳/FPS分别记录。
- 先做只读剖析和可复现测量，再提交最小解耦方案。
- 为推理和云端复核划分独立有界队列；明确满载时策略。
- 明确 sidecar 帧索引与视频 PTS 对齐规则。
- 验收：使用同一固定片段给出原始基线和修改后数据；短片不会因全速读完而只推理首帧；播放速度正确；框时间对齐；队列与丢帧指标可见。

负责人建议：DSH 分析后端采集/推理瓶颈并实现核心服务边界；Trae 独立负责浏览器实时/回放体验验证与指标展示，先不同时编辑同一文件。

### 阶段 B：证据与事件生命周期可靠性

目标：事件结束、停止、异常退出后，DB、视频和 sidecar 一致。

- 盘点所有触发、停止、异常、云端超时路径。
- 定义媒体写入完成标记、事件状态转换及启动时的孤儿文件/缺失文件诊断报告。
- 验收：模拟正常触发、手动 stop、进程异常中断和转码失败；每种结果可恢复或明确标失败，不出现静默“磁盘有 sidecar、DB 无事件”。

负责人建议：DSH 负责状态与媒体契约审查/后端实现；Trae 负责用 EventCenter/EventDetail 验证状态和失败信息。

### 阶段 C：摄像头场景配置 MVP

目标：把博文中的人工预标定思想接入现有 TrafficPlugin/规则引擎。

- 先确定配置 schema 和版本关联，再做最小前端编辑器。
- 先支持 ROI、停止线/计数线、车道方向、适用规则；物理速度标定独立评估。
- 规则引擎只读取场景配置，不把界面坐标逻辑写入算法模块。
- 验收：两种不同视频视角各自保存配置、重载仍一致；事件明确记录场景版本；单条规则可解释命中与未命中。

负责人建议：DSH 负责只读设计和后端 schema/规则契约；Trae 负责 SVG/Canvas 配置交互。契约评审后再并行开发。

### 阶段 D：统一车辆面板与事件中心

目标：实时预览、逐帧回放和事件详情使用同一份 VehicleSnapshot 映射。

- 展示 track ID、类别、速度及单位、方向、车牌和来源/置信度、当前规则状态。
- 选中侧栏车辆时联动高亮画面；历史/缺失字段准确显示“未采集/未识别”。
- 确认实时检测页与 EventCenter 的字段来自同一 API 契约。

负责人建议：Trae 主责 UI；DSH 对照 API 契约与后端序列化做交叉审查。

### 阶段 E：统计、模型评测和扩展模块治理

- 建立事件统计 API 和筛选导出，图表数字能回到事件明细。
- 对 YOLO、Tracker、OCR、红绿灯等模型建立运行清单、输入规格、设备兼容和固定验证样本。
- 只读盘点 `zhitong/`、K230、CARLA、数字孪生与各小程序，逐个标出主线/扩展/历史状态和运行证据；之后再决定哪些整合、冻结或维护。
- 评估模型版本、场景版本、规则版本和事件准确率的联合追踪。

## 7. 不作为近期目标的事项

- 一次性重写为微服务或迁移数据库。
- 同时扩张 K230、CARLA、数字孪生、小程序和交通检测主线。
- 在没有基线测试和实际部署需求时替换 YOLO/Tracking/OCR 模型。
- 将演示视频、插值框、模型文件清单当成真实性能或识别精度证据。
- 在没有审核和数据保留设计时默认长期保存车牌、人员或原始视频。

## 8. 协作与任务拆分原则

- 本方案由 ChatGPT 负责优先级与验收设计；DSH、Trae 担任开发主力。
- 每个实施 TASK 指定唯一文件负责人；并行工作仅限明确分开的目录/文件边界。
- L3/L4 任务先由 Agent 自主判断复杂度并按质量优先选择模型；不得为省 Token 降低必要能力；实际模型名无法可靠读取时如实报告。
- 任务只允许修改清单内文件；额外发现单独记录，不顺手扩展。
- 接受标准必须包含代码证据、运行/测试结果和真实数据验证；Agent 自报“完成”不等同于验收。
