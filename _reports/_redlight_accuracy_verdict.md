## 一、一句话结论

**"闯红灯成功率"低不是模型问题，而是灯态取错了对象**：原实现取"画面里
**任意一盏**灯"的最高优先级（红>绿>黄），而画面里同时有 6 盏灯（含 CAM-2 小窗
里那盏），**横向车道的红灯被当成了本方向的**。

修成"车道级（受控方向）灯态"（人工标一个 ROI，只认那盏灯）之后：

| 指标 | 修复前 | 修复后（4 轮实测） |
|---|---|---|
| 每循环 red_light 事件数 | **5~7 次** | **1 次** |
| 其中真违规检出 | 有（混在噪声里） | **3/3 循环 = 100%** |
| 误报 | 多次（t≈15.7~16.0s 时**真值是绿灯**） | **0** |
| 精确率 | 低（事件表几乎全被云端 rejected） | **100%** |
| 判色准确率（逐帧 vs 真值灯态） | 未测 | **95.6%~97.0%**（248~287 帧/轮） |
| 全片违规触发总数 | 十几条 | **每循环恰好 1 条，与真值完全一致** |

## 二、真值（来自 `ground_truth_dual.csv`，不是猜的）

| 项 | 值 |
|---|---|
| 灯态相位 | 红 0~13.5s → 绿 15.05~20.05s → 黄 20.05~25.05s → 红 25s 后 |
| **真闯红灯** | **`red_runner`（蓝色特斯拉）t=9.55s 越线，当时红灯 → 全片唯一 1 次** |
| 非违规对照 | `law_abiding`（红色奥迪）t=15.10s 越线，当时**绿灯** → 不该报 |
| 受控方向信号灯 | 世界 (-45.7,-64.3,5.15) → 标定投影到像素 **(1008,146)**；CNN 在 (1007,146) 判 red(0.998) —— **差 1 px** |

> （世界坐标 → 像素，误差 1 px）。

| 文件 | 改动 |
|---|---|
| `1\api\realtime_detector.py` | ① 灯框收集**上移到灯态汇总之前**（原来用的是上一帧判色结果，且会重复跑一次 CNN）；② 新增 `_light_in_rois()` + `_scene_light_state_from_cnn(rois=...)`：**只统计中心落在人工标注 `traffic_light_roi` 内的灯**；ROI 内漏检时**不退回全画面**（标记 `roi_miss`）；③ `/status` 新增 `traffic_light_scope` / `traffic_light_matched` / `traffic_light_state` 可观测字段；④ 新增**逐帧 trace**（`RT_TRACE_JSONL`，默认关闭零开销） |

| `1\api\vehicle_tracker.py` | `CentroidTracker._analyze_lane_position`：同样的**静止门**（最近 4 采样 < 2px 即视为静止 → 不判逆行）+ 1~2px 抖动当噪声（原判据只排除 `dx == 0`） |
| `1\api\violation_rules.py` | `_check_wrong_way` 调 `vehicle_tracker.update()` 时**传入真实画幅**（原来用默认 1280，而画面是 1920 → "对向车道"阈值严重偏左） |
| `_scripts\_evaluate_redlight.py` | **新建**：真值 CSV + trace 逐帧对齐 → 判色准确率 / 检出 / 重复 / 误报 / 精确率 |

## 四、★被推翻 / 更正的东西

| # | 旧结论或旧实现 | 更正 |
|---|---|---|
| O19 | （隐含假设）"场景灯态 = 画面里最危险的那盏灯" | ❌ 这是**误报之源**。灯态必须是**受控方向**的灯（车道级），否则横向车道的红灯会让本方向的每辆车都"闯红灯"。实测：修复前每循环 5~7 次 red_light |
| O20 | `behavior_engine` 的 `frame_width = 1280` 硬编码 | ❌ 画面是 1920 → "对向车道"阈值 896 远小于真实 1344，**正常行驶的车被判逆行**（落库 id=2406） |
| O21 | "方向类判据可以直接用 tracker 给的方向" | ❌ 停在停止线前等红灯的车，1~2px 抖动被读成方向 → 每循环 1 次逆行误报。**必须先判断"现在是否在动"**（且要用最近几个采样，不能用整段 history 的净位移——那辆车十几秒前开过 20 米） |
| O22 | "历史窗口里跨过停止线 = 抢黄灯" | ❌ 绿灯合法通过的车，等灯变黄仍会被判抢黄灯。必须要求**越线发生在最近几个采样内** |
| O23 | "x_std 启发式可以判逆行" | ⚠️ 只对**道路横向穿过画面**的机位成立。纵深机位下车辆因透视自然左漂（x 1550→1306、x_std≈80px），会被误判 |
| O24 | `_SESSION_HANDOFF.md` §二 "判色模型默认值已修复" 之外的遗留："**仍未解决的车道级灯态问题**" | ✅ **本轮已解决**（ROI 作用域 + 4 轮实测验证） |

## 七、仍未解决 / 风险

1. **上报滞后约 3 秒**：真值越线 9.55s（车尾过线 ≈10.6s），系统在 12.5~13.1s 报出。
   原因：检测循环只处理约 1/7 的帧（3 fps 处理 vs 20 fps 视频）+ `hold_sec=1.5`
   的持续确认。做证据链足够，做"实时告警"需提高处理帧率（换 yolov8n / 降 imgsz）。
2. **判色仍有 3%~4% 的危险方向错误**（红→黄 2~3 帧、红→绿 1~2 帧，每轮 250+ 帧）：
   CNN5 在灯头很小（10~16px）时会错。若要再压，需要"多帧投票"而不是逐帧判定。
3. **误报是按"每循环 1 次真违规"这个已知剧本核对的**：换视频必须重新标
   `traffic_light_roi` + `stop_line_y`，否则 §四的 O19 会立刻复现。
4. **`running_yellow` / `speeding` 等其它规则本轮只做了"不误报"层面的收敛**，
   没有像闯红灯这样逐帧评估。
5. **逆行判定的根本问题未解**：纵深机位下缺少"车道级方向"依据（需要车道线标注
   + 车道方向配置），本轮是"判不准就不判"。
